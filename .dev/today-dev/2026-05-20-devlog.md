## 1. 학습한 내용 및 활동 결과

### 1-1. Phase 2 팀 빌딩 기능의 구조적 통합

Phase 1에서 구현된 참여자 명단 관리 시스템에 Phase 2의 팀 빌딩 알고리즘을 성공적으로 통합하였다. 기존에 구현되었던 Snake Draft 알고리즘(`snakeDraft.js`)과 학년 가중치 필터(`yearWeighting.js`)를 활용하여, MatchPage 컴포넌트에서 조건부로 TeamBuilder UI를 렌더링하는 통합 구조를 완성하였다. 특히, 경기 상태('모집 중')와 참여자 수(2명 이상) 조건을 검증한 후에만 팀 배정 기능을 활성화함으로써 사용자 경험과 데이터 무결성을 동시에 확보하는 방식을 적용하였다. 이를 통해 사용자는 참여자를 등록하는 즉시 자동으로 생성된 팀 구성을 시각적으로 확인할 수 있게 되었으며, 학년 가중치 조정 및 재배정 버튼을 통해 최적의 팀 조합을 능동적으로 탐색할 수 있는 인터페이스를 제공하게 되었다(학습 내용 및 활동 결과: 약 270자).

### 1-2. TeamBuilder 컴포넌트의 재사용 가능한 설계 패턴

TeamBuilder 컴포넌트는 props로 받은 참여자 배열만으로 독립적으로 팀 배정 기능을 수행하도록 설계하였으며, 이는 향후 다른 페이지에서도 이 컴포넌트를 재사용할 수 있음을 의미한다. `useMemo`를 활용하여 매개변수(yearWeight, iterations, refreshSeed) 변경 시에만 팀 빌딩 알고리즘을 재실행하도록 최적화하였으므로, 렌더링 시 불필요한 계산을 피할 수 있다. 또한 매개변수가 직관적인 범위(학년 가중치 0~2, 반복 횟수 10~100)로 제한되어 있어 사용자가 시뮬레이션을 통해 팀 배정의 다양한 시나리오를 안전하게 탐색할 수 있다. 컴포넌트 계층 관점에서 보면, 데이터 정규화(skillScore, year를 숫자로 변환) → 알고리즘 실행(`buildBalancedTeams`) → UI 렌더링(Card + List) 순서로 명확히 분리되어 있어 유지보수성이 높다(학습 내용: 약 230자).

### 1-3. MatchPage에서의 조건부 렌더링 및 레이아웃 통합

MatchPage에 TeamBuilder를 통합하면서 레이아웃 구조를 다음과 같이 설계하였다: **참여자 목록 → 팀 빌딩(조건부) → 경기 관리 액션**. 이 순서는 사용자의 정보 처리 흐름과 일치하는데, 참여자들을 먼저 확인한 후 자동으로 생성된 팀 구성을 보고, 필요하면 경기 상태를 변경하는 자연스러운 워크플로우를 유도한다. 조건부 렌더링 로직(`currentMatch.status === 'recruiting' && currentMatch.participants.length >= 2`)은 TeamBuilder를 표시할 최소 요건을 명확히 함으로써, 데이터가 불충분한 상태에서의 오류 가능성을 사전에 차단한다. 또한 경기 상태가 '준비 완료'로 변경되면 TeamBuilder가 자동으로 숨겨지므로, 경기가 진행 중인 상태에서는 팀 구성이 우발적으로 변경되지 않도록 보호된다(학습 내용: 약 280자).

## 2. 소스코드 캡처

### 소스코드 캡처 ①: `snakeDraft.js` — Snake Draft 알고리즘 핵심 로직

```javascript
// src/utils/snakeDraft.js

/**
 * 2팀 Snake Draft 패턴 인덱스
 * A, B, B, A 반복 (지그재그 방식)
 * @param {number} index
 * @returns {0|1}
 */
const getSnakeTeamIndex = (index) => {
  const pattern = [0, 1, 1, 0];
  return pattern[index % pattern.length];
};

/**
 * 단일 스네이크 드래프트 실행
 * @param {Array} participants
 * @returns {{teamA:Array, teamB:Array}}
 */
export const runSnakeDraft = (participants) => {
  const prepared = shuffle(participants).sort((a, b) => {
    const skillGap = Number(b.skillScore || 3) - Number(a.skillScore || 3);
    if (skillGap !== 0) return skillGap;
    return Number(a.year || 0) - Number(b.year || 0);
  });

  const teamA = [];
  const teamB = [];

  prepared.forEach((player, index) => {
    const targetTeam = getSnakeTeamIndex(index) === 0 ? teamA : teamB;
    targetTeam.push(player);
  });

  return { teamA, teamB };
};
```

> **학습 포인트**: Snake Draft는 [0, 1, 1, 0] 패턴을 반복하여 A팀과 B팀에 번갈아 배정하는 방식이다. 이는 직선 드래프트[0, 1, 2, 3, ...]보다 팀의 총 실력을 더 균형잡게 만든다. 먼저 실력 점수로 내림차순 정렬 후 학년으로 차선책 정렬하여, 비슷한 실력의 선수들 중에서 학년 다양성을 확보한다.

### 소스코드 캡처 ②: `yearWeighting.js` — 학년 가중치 기반 밸런스 점수 계산

```javascript
// src/utils/yearWeighting.js

/**
 * 팀 밸런스 점수(낮을수록 좋음)
 * 실력 차이 + 학년 편향 페널티의 합
 * @param {Array} teamA
 * @param {Array} teamB
 * @param {number} yearWeight - 학년 페널티 가중치
 * @returns {object}
 */
export const getBalanceScore = (teamA, teamB, yearWeight = 0.6) => {
  const totalSkillA = getTotalSkill(teamA);
  const totalSkillB = getTotalSkill(teamB);
  const skillDiff = Math.abs(totalSkillA - totalSkillB);
  
  const yearPenalty = getYearBalancePenalty(teamA, teamB, yearWeight);
  const score = skillDiff + yearPenalty;

  return {
    score,                  // 전체 밸런스 점수
    skillDiff,             // 실력 차이만
    yearPenalty,           // 학년 편향 페널티만
    avgYearA: getAverageYear(teamA),
    avgYearB: getAverageYear(teamB),
    totalSkillA,
    totalSkillB,
  };
};

/**
 * 학년 편차 페널티 계산
 */
export const getYearBalancePenalty = (teamA, teamB, yearWeight = 0.6) => {
  const avgYearA = getAverageYear(teamA);
  const avgYearB = getAverageYear(teamB);
  const yearDiff = Math.abs(avgYearA - avgYearB);
  return yearDiff * yearWeight;
};
```

> **학습 포인트**: 밸런스 점수는 `실력 차이 + (학년 차이 × 가중치)`로 계산된다. 이를 통해 실력 균형을 우선하면서도 학년 쏠림을 제어할 수 있다. yearWeight를 UI에서 조정 가능하게 하면 사용자가 원하는 정도의 학년 다양성을 선택할 수 있다.

### 소스코드 캡처 ③: `TeamBuilder.jsx` — 팀 빌딩 UI 컴포넌트 통합

```javascript
// src/components/TeamBuilder.jsx (핵심 부분 발췌)

function TeamBuilder({ participants = [] }) {
  const [yearWeight, setYearWeight] = useState(0.6);
  const [iterations, setIterations] = useState(30);
  const [refreshSeed, setRefreshSeed] = useState(0);

  // 입력 데이터 정규화 및 메모이제이션
  const normalizedParticipants = useMemo(() => {
    return participants.map((p) => ({
      ...p,
      skillScore: Number(p.skillScore || 3),
      year: Number(p.year || 1),
    }));
  }, [participants]);

  // 팀 빌딩 결과 계산 (매개변수 변경 시에만 재실행)
  const result = useMemo(() => {
    if (normalizedParticipants.length < 2) return null;
    return buildBalancedTeams(normalizedParticipants, {
      yearWeight,
      iterations,
      seed: refreshSeed,
    });
  }, [normalizedParticipants, yearWeight, iterations, refreshSeed]);

  return (
    <div className="team-builder-root">
      {/* 학년 가중치 조정 슬라이더 */}
      <label className="team-builder-label">
        학년 가중치 ({Number(yearWeight).toFixed(1)})
        <input
          type="range"
          min="0"
          max="2"
          step="0.1"
          value={yearWeight}
          onChange={(e) => setYearWeight(Number(e.target.value))}
        />
      </label>

      {/* 반복 횟수 조정 슬라이더 */}
      <label className="team-builder-label">
        반복 횟수 ({iterations})
        <input
          type="range"
          min="10"
          max="100"
          step="5"
          value={iterations}
          onChange={(e) => setIterations(Number(e.target.value))}
        />
      </label>

      {/* 재배정 버튼 */}
      <Button variant="primary" onClick={() => setRefreshSeed((v) => v + 1)}>
        재배정
      </Button>

      {/* 팀 A, B 렌더링 */}
      {result && (
        <>
          <Card header={<h3>📊 밸런스 지표</h3>}>
            <div className="team-builder-metrics">
              <div>총 밸런스 점수: <strong>{result.metrics.score.toFixed(2)}</strong></div>
              <div>실력 차이: <strong>{result.metrics.skillDiff.toFixed(2)}</strong></div>
              <div>학년 페널티: <strong>{result.metrics.yearPenalty.toFixed(2)}</strong></div>
            </div>
          </Card>

          <div className="team-builder-grid">
            <Card variant="team-a" header={<h3>🔵 팀 A ({result.teamA.length})</h3>}>
              <ul className="team-builder-list">
                {result.teamA.map((player) => (
                  <li key={player.id} className="team-builder-player">
                    <span>{player.nickname}</span>
                    <span className="team-builder-badge">{player.position}</span>
                    <span className="team-builder-badge">{player.year}학년</span>
                    <span className="team-builder-badge">실력 {player.skillScore}</span>
                  </li>
                ))}
              </ul>
            </Card>

            <Card variant="team-b" header={<h3>🔴 팀 B ({result.teamB.length})</h3>}>
              <ul className="team-builder-list">
                {result.teamB.map((player) => (
                  <li key={player.id} className="team-builder-player">
                    <span>{player.nickname}</span>
                    <span className="team-builder-badge">{player.position}</span>
                    <span className="team-builder-badge">{player.year}학년</span>
                    <span className="team-builder-badge">실력 {player.skillScore}</span>
                  </li>
                ))}
              </ul>
            </Card>
          </div>
        </>
      )}
    </div>
  );
}
```

> **학습 포인트**: `useMemo`를 이용한 계산 최적화는 팀 빌딩 알고리즘이 30회 반복(iterations 기본값)로 비용이 크다는 점을 고려한 것이다. refreshSeed 상태 변수는 실제 데이터를 바꾸지 않고 의존성 배열에 포함시켜 강제로 재계산을 트리거하는 패턴으로, 동일한 입력값에 대해 다른 결과를 얻고자 할 때 유용하다.

### 이슈 #1 — [해결] TeamBuilder import 경로 오류로 인한 컴포넌트 로드 실패

| 항목 | 내용 |
|------|------|
| **발생 위치** | `src/pages/MatchPage.jsx` |
| **발생 시각** | 2026-05-20 14:35 |
| **증상** | TeamBuilder를 import하지 않았을 때 컴포넌트가 undefined로 인식되어 렌더링 오류 발생 |
| **상태** | ✅ 해결 완료 |

**원인 분석**

MatchPage에서 TeamBuilder를 사용하기 위해 컴포넌트를 렌더링하는 JSX 코드는 작성했으나, import 문에 TeamBuilder를 추가하지 않았다. 리액트에서는 JSX에 사용된 모든 컴포넌트를 반드시 같은 파일에서 import하거나 동일한 스코프 내에 정의해야 하는데, 이 규칙을 놓쳤다. 결과적으로 런타임 오류 "TeamBuilder is not defined"가 발생하여 MatchPage 전체가 렌더링되지 않았다.

**해결 방법**

MatchPage의 import 문을 다음과 같이 수정하여 TeamBuilder를 추가했다:

```javascript
// 수정 전 (오류)
import {
  Layout,
  Container,
  MatchForm,
  ParticipantForm,
  ParticipantList,
  MatchActions,
  // TeamBuilder 누락
} from '../components';

// 수정 후 (정상)
import {
  Layout,
  Container,
  MatchForm,
  ParticipantForm,
  ParticipantList,
  MatchActions,
  TeamBuilder,  // 추가
} from '../components';
```

이후 React DevTools 및 브라우저 콘솔에서 오류가 완전히 제거됨을 확인했고, MatchPage의 조건부 렌더링 로직이 정상 작동하여 팀 빌딩 섹션이 올바르게 표시되었다(해결 방법 설명: 약 180자).

### 이슈 #2 — [해결] TeamBuilder에 전달되는 참여자 데이터 타입 불일치

| 항목 | 내용 |
|------|------|
| **발생 위치** | `src/components/TeamBuilder.jsx` |
| **발생 시각** | 2026-05-20 14:52 |
| **증상** | 팀 빌딩 결과에서 선수의 학년(year)이 문자열로 인식되어 밸런스 점수 계산이 NaN을 반환함 |
| **상태** | ✅ 해결 완료 |

**원인 분석**

ParticipantForm에서 사용자가 입력한 학년과 실력 점수 데이터가 HTML input 요소의 기본 반환 타입인 문자열로 저장되어 있었다. 이 문자열 데이터가 그대로 `buildBalancedTeams` 함수에 전달되면, `getAverageYear` 함수 내에서 `Number(player.year || 0)`로 변환되지만, 이미 데이터가 저장된 상태에서는 일관성 문제가 발생할 수 있었다. 특히 반복 계산 시 데이터 타입 변환 오버헤드가 누적되고, 모달이나 캐시된 값을 사용할 때 타입이 혼재될 수 있다는 우려가 있었다.

**해결 방법**

TeamBuilder 컴포넌트 내부에서 `useMemo`를 활용하여 입력받은 participants 배열을 정규화하는 단계를 추가했다:

```javascript
// src/components/TeamBuilder.jsx
const normalizedParticipants = useMemo(() => {
  return participants.map((p) => ({
    ...p,
    skillScore: Number(p.skillScore || 3),  // 숫자로 강제 변환
    year: Number(p.year || 1),              // 숫자로 강제 변환
  }));
}, [participants]);

const result = useMemo(() => {
  if (normalizedParticipants.length < 2) return null;
  return buildBalancedTeams(normalizedParticipants, {
    yearWeight,
    iterations,
    seed: refreshSeed,
  });
}, [normalizedParticipants, yearWeight, iterations, refreshSeed]);
```

이 방식은 컴포넌트 계층에서 데이터 타입을 정규화하므로, 하위 알고리즘 함수들은 항상 일관된 타입의 입력값을 받게 된다. 정규화된 배열은 메모이제이션되어 불필요한 재변환을 피할 수 있으며, 데이터 무결성과 성능을 동시에 확보할 수 있다(해결 방법 설명: 약 220자).

### 이슈 #3 — [해결] 팀 빌딩 결과의 일관성 부족 (매번 다른 결과 출력)

| 항목 | 내용 |
|------|------|
| **발생 위치** | `src/utils/snakeDraft.js` — `runSnakeDraft` 함수 |
| **발생 시각** | 2026-05-20 15:18 |
| **증상** | 참여자 목록이나 매개변수가 변경되지 않았는데도 팀 배정 결과가 매번 달라짐 |
| **상태** | ✅ 해결 완료 (설계 의도 확인) |

**원인 분석**

이 현상은 실제로는 버그가 아니라 설계 의도였다. `runSnakeDraft` 함수가 매번 실행될 때마다 `shuffle(participants)`로 배열을 무작위로 섞기 때문에, 동일한 입력값으로도 다른 팀 구성이 생성되는 것이다. 이를 보정하기 위해 `buildBalancedTeams` 함수는 iterations 횟수만큼 반복 실행하여 가장 낮은 밸런스 점수를 가진 결과를 최종 반환한다. 그러나 iterations가 30번이나 이루어지면서 계산 시간이 누적되고, 사용자가 버튼을 여러 번 클릭할 때마다 다른 결과가 나온다는 혼동이 발생했다.

**해결 방법**

이 이슈를 근본적으로 해결하기 위해 TeamBuilder에 `refreshSeed` 상태 변수를 도입했다. 이는 **재배정 버튼**을 클릭할 때만 새로운 팀 조합을 계산하고, 매개변수(yearWeight, iterations)가 변경될 때만 자동으로 재계산되도록 한 것이다:

```javascript
// src/components/TeamBuilder.jsx
const [refreshSeed, setRefreshSeed] = useState(0);

const result = useMemo(() => {
  if (normalizedParticipants.length < 2) return null;
  return buildBalancedTeams(normalizedParticipants, {
    yearWeight,
    iterations,
    seed: refreshSeed,  // 이 값이 변할 때만 재계산
  });
}, [normalizedParticipants, yearWeight, iterations, refreshSeed]);

// 재배정 버튼 클릭 시
<Button variant="primary" onClick={() => setRefreshSeed((v) => v + 1)}>
  재배정
</Button>
```

`refreshSeed`는 실제 데이터를 변경하지 않지만, `useMemo` 의존성 배열에 포함되어 있어서 클릭할 때마다 강제로 재계산을 트리거한다. 이를 통해 사용자는 명시적으로 '재배정' 버튼을 클릭했을 때만 다른 팀 구성을 보게 되며, 슬라이더로 매개변수를 조정하면 즉시 반응하면서도 계산 횟수가 불필요하게 증가하지 않는다(해결 방법 설명: 약 200자).

### 이슈 #4 — [해결] 조건부 렌더링이 없어서 참여자 부족 상황에서 오류 발생

| 항목 | 내용 |
|------|------|
| **발생 위치** | `src/pages/MatchPage.jsx` |
| **발생 시각** | 2026-05-20 15:35 |
| **증상** | 참여자가 1명 이하일 때 TeamBuilder가 렌더링되어, 팀 배정 불가능 상태에서도 "최소 2명 이상" 경고만 표시됨 |
| **상태** | ✅ 해결 완료 |

**원인 분석**

초기 구현에서는 MatchPage에서 항상 TeamBuilder를 렌더링했기 때문에, 참여자 수가 2명 미만인 상황에서도 컴포넌트가 로드되었다. TeamBuilder 내부에는 최소 인원 확인 로직이 있어서 "최소 2명 이상 참가해야 팀 배정이 가능합니다" 메시지를 표시했지만, 이는 불필요한 컴포넌트 초기화와 불완전한 UI 상태를 만들었다. 더 나아가, 경기 상태가 '준비 완료'인 경우에도 TeamBuilder가 계속 렌더링되어 이미 확정된 팀 구성이 다시 변경될 가능성이 있었다.

**해결 방법**

MatchPage에서 TeamBuilder를 렌더링하기 전에 명확한 조건 검사를 추가했다:

```javascript
// src/pages/MatchPage.jsx
{currentMatch.status === 'recruiting' && currentMatch.participants.length >= 2 && (
  <div style={{ marginBottom: 'var(--spacing-6)' }}>
    <TeamBuilder participants={currentMatch.participants} />
  </div>
)}
```

이 조건부 렌더링으로 다음의 효과를 얻었다:
1. 참여자가 2명 미만이면 TeamBuilder를 아예 렌더링하지 않아 불필요한 계산과 메모리 사용을 방지
2. 경기 상태가 '준비 완료'로 바뀌면 TeamBuilder가 화면에서 자동으로 제거되어, 확정된 팀 구성이 우발적으로 변경되는 상황 차단
3. 사용자 경험 관점에서도 '모집 중' 상태에서만 팀 구성을 수정할 수 있다는 의도를 명확히 함(해결 방법 설명: 약 190자).

### 이슈 #5 — [진행 중] 팀 배정 결과의 영속성 부재로 인한 기능 제약

| 항목 | 내용 |
|------|------|
| **발생 위치** | `src/components/TeamBuilder.jsx` / `src/hooks/useMatchData.js` |
| **발생 시각** | 2026-05-20 16:05 |
| **증상** | 팀 빌딩 결과가 메모리상 존재하지만 LocalStorage에 저장되지 않아, 페이지 새로고침 시 팀 구성 데이터 소실 |
| **상태** | ⚠️ 진행 중 — 다음 개발 사이클에서 처리 예정 |

**원인 분석**

TeamBuilder는 현재 props로 받은 참여자 배열을 기반으로 실시간 계산만 수행할 뿐, 결과를 경기 데이터에 저장하는 기능이 없다. 사용자가 '재배정' 버튼으로 만족할 만한 팀 구성을 찾았더라도, 이를 저장하는 방법이 없어서 페이지를 새로고침하면 계산 결과가 초기화된다. 이는 Phase 3(전술 배치도)과 Phase 4(별점 리뷰)에서 팀 구성 정보가 필요할 때 문제가 될 수 있다. 또한 '팀 구성 확정' 같은 명시적인 사용자 액션이 없어서, 팀 빌딩 결과의 최종성이 불명확하다는 UX 문제도 있다.

**조치 예정**

다음 세션에서 다음과 같은 방식으로 개선할 예정이다:

```javascript
// 예정된 개선 구조
// 1. useMatchData 훅에 팀 저장 함수 추가
const saveTeamAssignment = (matchId, { teamA, teamB, metrics }) => {
  setMatches((prev) =>
    prev.map((match) =>
      match.id === matchId
        ? {
            ...match,
            teamAssignment: { teamA, teamB, metrics, savedAt: new Date().toISOString() },
          }
        : match
    )
  );
};

// 2. TeamBuilder에 '팀 구성 확정' 버튼 추가
<Button variant="success" onClick={() => {
  saveTeamAssignment(currentMatch.id, result);
  alert('팀 구성이 저장되었습니다!');
}}>
  팀 구성 확정
</Button>

// 3. 경기 상태 변경 시 팀 구성 잠금
```

이렇게 하면 사용자가 명시적으로 팀을 확정하는 액션이 생기고, Phase 3 전술 배치도에서는 저장된 팀 정보를 불러올 수 있으며, Phase 4 별점 리뷰에서는 누가 같은 팀이었는지 정확히 파악할 수 있게 된다(조치 예정 설명: 약 200자).

## 4. 고찰 및 추후 개발 계획

### 2-1. 고찰

Phase 2 개발을 통해 복잡한 비즈니스 로직(팀 빌딩 알고리즘)을 리액트 컴포넌트 계층과 명확히 분리하는 방식의 중요성을 재확인하였다. `snakeDraft.js`와 `yearWeighting.js`는 순수 JavaScript 함수로만 이루어져 있어서, React와 무관하게 테스트하고 재사용할 수 있으며 이는 코드 품질을 높인다. 또한 `useMemo`를 통한 메모이제이션은 팀 빌딩 알고리즘의 높은 계산 비용을 감안할 때 매우 효과적이었다. 한편, 현재 구현에서는 팀 배정 결과를 LocalStorage에 저장하지 않고 있어, 페이지 새로고침 시 팀 구성이 사라지는 한계가 있다. 향후에는 사용자가 '팀 구성 확정' 버튼으로 경기에 팀 정보를 저장하고, 이를 Phase 3 전술 배치도와 Phase 4 별점 리뷰 단계에서 활용하는 방식으로 개선할 필요가 있다. 또한 반복 횟수(iterations)를 과도하게 크게 설정하면 브라우저 UI가 일시적으로 응답하지 않을 수 있으므로, 비동기 처리나 Web Worker를 도입하는 최적화도 고려해볼 만하다(고찰 내용: 약 280자).
